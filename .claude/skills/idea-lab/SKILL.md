# idea-lab (될 놈 실험실)

위프 팀의 "될 놈 실험실 Process"(릴스 `Ddi6CRfTQBY` 11~14초 흐름도)를 1인용으로 옮긴 스킬이다. 조사는 서브에이전트가, **판정과 검증은 메인이**, 최종 확인은 사용자가 한다.

세부 규칙은 필요할 때만 읽는다:
- `references/commands.md` — `LAB` 명령 전체와 주의사항
- `references/harvest.md` — 1단계 발굴(신호 하베스트·증거 세 개·마켓 캐시·사전 필터)
- `templates/WHATIF_PROMPT.md`·`templates/IDEATION_METHODS.md` — 발상법 8가지 절차(기법별 `origin` 표시)
- `templates/REVENUE_REVIEW_PROMPT.md` — 지불 실패로 버린 아이디어의 지불자 재검토
- `references/research.md` — 3단계 조사·채점 기준표·예외 후보·피벗
- `references/fdt.md` — 4단계 표본 검증·정성 게이트·묶음·가짜 문 테스트
- `references/logins.md` — 로그인 출처(Aside) 규칙·세션 점검·`LAB gated`·사이트별 요령. **읽기만 한다**
- `templates/` — 조사원·하베스터 공통 지시문(`RESEARCH_PROMPT.md`, `HARVEST_PROMPT.md`)과 FDT 페이지(`fdt.html`). `LAB init`이 지시문을 `lab/batches/`로 복사한다

## 원칙
- 한 바퀴의 목표는 **프로토타입 우선순위 리스트**. 통과한 것만 `idea-blueprint`로 넘긴다
- **빨리 많이 버린다.** 애매하면 Drop하거나 대기시킨다
- **편견 없이 넓게 찾는다.** 하베스트의 30% 이상은 낙인·비주류·외곽의 **합법** 시장(성인·장례·점술·리셀·사회적 약자·서브컬처 등)에 둔다. 불법이거나 불법을 돕는 것은 제외 → `references/harvest.md` "넓게 보기"
- **근거 없이 채점하지 않는다.** 조사 뒤에 채점하고, 추정이 섞이면 보고에 "추정"이라고 적는다
- **조사원 근거를 그대로 믿지 않는다.** 4단계로 올리기 전에 메인이 핵심 근거를 직접 연다(표본 검증). 실측상 "경쟁 제품이 없다"와 가격 단위가 가장 자주 틀린다
- **규칙이 의견보다 우선한다.** need ≤ 2 또는 수익성(max(revenue, fame)) ≤ 2면 Drop. **need는 고통 또는 욕망**(욕망은 행동 증거로), **pain 관문은 원문 대신 행동 증거도 인정**, **비싸거나 불만 많은 유료 경쟁은 이길 틈(beatable)**, **붐비는 시장도 유통 우위+약점+좁은 첫 자리가 모두 있으면 진입(crowded_winnable)**, **해외 시장도 본다**(`market` global/both, 대시보드 🌍), 직접 만드는 유입 길(`dist_path`: 무료 도구 검색 유입·콘텐츠·만드는 과정 공개)도 dist로 인정, 1인 운영 부담(`ops`)·수익 모델 종류(`revenue_math.model`)·왜 지금(`why_now`, 증거가 얇으면 `wait` → 타이밍 대기)을 함께 본다. **수익성은 두 길**: 유료 고객으로 월 300만 원(revenue) 또는 무료라도 유명해져 광고·파생 제품·제휴·인수로 돈이 되는 길(fame, 기본 목표 1년 월 사용자 1만 명). 예외 후보를 살릴지는 사용자가 정한다
- 모든 이동은 `LAB move ... --reason "근거"`. 보드는 `LAB`으로만 고친다
- 사용자에게 시키는 일: 최초 설정(창업자 프로필·분석 도구 — 필요한 순간 한 번씩), FDT 트래픽, 로그인이 필요한 출처 열어 주기, 판정 확인. 사용자 이름으로 외부에 연락하는 일은 초안까지만
- **사용량을 아낀다.** 조사원·하베스터는 Sonnet, 동시 4명 이하, 하위 에이전트 금지(프롬프트에 직접 적는다), 결과는 한 줄씩 즉시 저장(`.jsonl`)

## 역할
| 역할 | 누가 | 맡는 일 |
|---|---|---|
| 하베스터 | 서브에이전트(Sonnet) | 1단계 신호 수집 |
| 리서처 | 서브에이전트(Sonnet) | 3단계 조사, 4단계 원문 보강 |
| 결정권자·검증자 | 메인 Claude | 채점 확정, 선검증·표본 검증, 판정 초안, 마켓 캐시, 로그인 출처(Aside, 읽기 전용 — `LAB gated`) |
| 확인자 | 사용자 | 예외·피벗 승인, 트래픽, 최종 판정 |

## 5단계 흐름

**1단계 Ideation** — 사용자가 준 아이디어는 P/S를 한 문장씩 채워 `LAB add`. 직접 발굴은 신호 하베스트로 한다: 후보마다 불편·지불·빈틈 증거 세 개, 하베스터별 통과율(`LAB stats`)과 고갈 지도(`LAB stats --tags`)로 비중을 정한다 → `references/harvest.md`

**선검증** — 조사원에게 보내기 전에 메인이 모든 후보를 기능 키워드로 1번씩 검색하고, 마켓 기반 후보는 Aside로 마켓 검색 목록도 뜬다. 이미 있는 건 바로 Drop(실측: 조사 통과 10개 중 7개가 기존 제품) → `references/harvest.md`

**2단계 Incubating** — "P-Code와 S-Code가 한 문장씩 명확한가?" 명확하면 `incubating` 후 바로 `brainstorming`(`LAB import`는 신호가 있으면 자동 통과). 두 번 불명확하면 Drop

**3단계 Brainstorming** — 리서처 조사 → `LAB apply`로 채점·자동 Drop → `LAB rank`로 순서 확인(평균 need·revenue·tenx·dist, 같으면 fit) → 올릴 것은 표본 검증 후 `move .. filtering`, `LAB rank --apply`로 우선순위 → `references/research.md`

**발상 두 갈래** — ①불만 원문 하베스트(`templates/HARVEST_PROMPT.md`) ②발상법 8가지 — 가정법(`templates/WHATIF_PROMPT.md`)과 SCAMPER·역브레인스토밍·가치사슬 쪼개기·극단 사용자·두 흐름 교차·JTBD·제약 추가·AI 신제품 활용(`templates/IDEATION_METHODS.md`), `origin`으로 저장 → 대시보드·목록에 기법 이름 칩 표시. 둘 다 같은 관문을 지나며, 수익은 쓰는 사람 구독만이 아니라 `references/research.md`의 **수익 구조 카탈로그**(반대편 과금·후원 배포·정부 바우처·인증 배지·데이터·화이트라벨 등)와 지불자(`payer`)까지 본다

- **지불 실패로 버린 아이디어 재검토**: `templates/REVENUE_REVIEW_PROMPT.md`(반대편·후원사·정부·데이터 구매자·파트너 지불자 점검) → revive면 `LAB move <id> brainstorming --force --reason "지불자 재검토"` → `LAB apply` → 표본 검증 → 레드팀
- **보완은 메인이 판단해 바로 적용하고 회차별로 기록한다(사용자 위임 2026-09-26)**: 점검마다 바꾼 것(기준·과정·도구·스킬)을 `lab/rounds/IMPROVEMENTS.md`에 '## #N' 절로 덧붙인다 — 사용자가 물으면 이 파일로 답한다. 사용자 승인은 필요 없지만 다양성·전문성·정확성을 해치는 변경은 하지 않는다
- **보완 점검 때 과정도 점검한다(사용자 지시 2026-09-26)**: 기준점 사각지대와 함께 **속도(병목 단계·단계별 소요·생존까지 걸린 시간)와 검증 방법(어디서 오판했나·놓친 확인)**도 개선점으로 적어 사용자에게 먼저 보여 준다. 단 속도를 올리는 안은 **다양성(한 유형에 몰지 않기)·전문성(업종 규정·실무 확인)·정확성(원문·판례·데이터 직접 확인)**을 해치지 않을 때만 제안한다
- **속도 규칙(사용자 승인 2026-09-26: A·B·C·E, D는 다양성을 위해 쓰지 않음)**: A 조사+레드팀을 한 조사원이 한 줄에(`audit_verdict`) → 메인은 apply·audit·verify만 / B 발굴 단계에서 '무료 공식 기능·1만+ 운영 중 경쟁·법 금지'를 검색 2번 안에 먼저 확인해 바로 버림 / C 심층 조사는 한 조사원에게 5~6개씩 묶어 보냄 / E 사용자 보고는 새로 살아남은 아이디어(4단계·4-b 진입)와 보완 점검 때만 짧게 — 중간 결과마다 보고하지 않는다. 발굴 비중은 한 유형에 몰지 않고 발상법·하베스트를 고르게 돌린다
- **중복 먼저 확인(보완 #12)**: 발굴 웨이브를 보내기 전에 메인이 `scripts/knowledge.py`로 `lab/knowledge/titles.tsv`(id·단계·기법·제목·탈락 사유)를 새로 만들고, 발굴자는 후보마다 핵심 명사로 grep해(통째로 읽지 않음) 예전 탈락 사유를 뒤집는 새 증거가 없으면 적지 않는다(재발굴된 중복: i2160=i1396, i2150≈i1274, i2173≈i2015)
- **100개 묶음 깔때기(사용자 승인 2026-09-27, 보완 #15)**: 조금씩 찾고 바로 검증하던 방식을 바꿔, ① 발굴만 먼저 — 할당표(기법 9+하베스트 각 6~15, 해외 25+, 소비자 30+·B2B 30+·크리에이터·모임·공공 15+, 한 세부 분야 15 이하)대로 웨이브(25~30줄)를 돌려 사전 필터 통과·보류 100개 ② 1차 카드 선별로 중복 제거·분야별 묶음·상위 25~30개 ③ 같은 분야 5~6개씩 심층 조사+레드팀 ④ 묶음 끝에 보완 점검. 실수 조기 발견 장치: 웨이브마다 `LAB lint`(개념 중복 10%·필수 칸 누락 20% 초과 시 그 웨이브 재실행), 20개 파일럿 점검(메인이 무작위 3개의 탈락 사유 3가지 직접 확인), 50개 중간 점검(누적 분포를 할당표와 비교해 남은 웨이브 재배정), 선별 보정(선별 탈락 무작위 3개도 심층 조사). 계획·진행은 `lab/batches/B<번호>_plan.md`
- **지불 관문 두 길**: 돈을 낸 선례(`pay_evidence`) 또는 **가치 기반**(`value_evidence`: 연 손실 출처 2건 + 빈도 + 결정권자 + 가격 ≤ 손실 10%). 가치 기반으로만 통과한 아이디어는 대시보드 `4-b 💳 지불 검증 필요` 칸에 모이고, FDT에서 선결제 1건 이상이 나와야 go(`LAB fdt`가 강제). 살아있는 수는 '확정(선례 있음)'과 '💳 지불 검증 필요'를 나눠 보고한다
- **새 발상법은 사용자 허락 뒤에만**: 가정법 외의 발상법(SCAMPER, 역브레인스토밍 등)을 쓰려면 먼저 목록·예시를 사용자에게 보여 주고 허락받은 것만 템플릿으로 만든다(사용자 지시 2026-09-25)

**4단계 Filtering** — 진입 전 **될놈 관문 6항목**(`LAB gate`: 경쟁·불편 원문 3건·지불·수익 계산·4주 제작·레드팀) — 표본 검증 → 레드팀 감사(`templates/AUDIT_PROMPT.md` → `LAB audit`) → 메인 확정. 레드팀이 pain을 '원문이 로그인 카페 뒤라 못 봄'으로 떨어뜨리면 메인이 Aside로 네이버 카페 검색 탭 → 글의 `ArticleRead` 프레임 본문을 **읽기만** 해서 원문을 확보한 뒤 판정한다(보완 점검 #6: i1462 원문 7건 확보로 통과). 진입 후 정성 게이트 → 묶음(`LAB bundle`) → `LAB fdt-scaffold`로 랜딩페이지 → 배포·트래픽 → `LAB fdt`로 판정. 4·5단계 자리 수는 `max_parallel`(0 = 제한 없음, 이 보드는 0). 제한이 없으면 관문은 표본 검증뿐이고, FDT 순서는 `LAB rank`가 정한다 → `references/fdt.md`

**5단계 2일마다 리뷰** — `LAB due`로 오늘 볼 것. 가안(prelim)에서 출발해 FDT 결과로 확정:
- `easy`(5=따라 하기 어려움): 경쟁사가 금방 할 수 있나, 사용자 확보·운영 비용, 규제 / 데이터 확보, 최신 AI로 가능한가, 1인 기술력으로 되나
- `moat`: 네트워크 효과·쌓이는 데이터·독점 기술·규모의 경제·브랜드·전환 비용
- `scale`: 작게 시작해도 커질 길, 인접 타깃·기능
- 판정: 예 → `done --priority N` / 아니오 → `dropped` / 보완 → `review --verdict retry`(2일 뒤 재리뷰)

## 한 바퀴 마무리
1. DONE을 우선순위 표로(제목·P/S·FDT 가입률·easy/moat/scale·이유)
2. 1순위는 `idea-blueprint`로(조사 파일 함께)
3. `LAB exceptions`로 예외 후보·피벗안을 보여 주고 사용자가 고른 것만 살린다
4. `LAB stats`·`LAB stats --tags`·`LAB stats --stages`로 다음 바퀴 하베스터 비중·고갈 분야·단계별 오판율을 본다
6. `LAB drops --md`(Drop 사유 유형별 정리)와 `LAB exceptions --md`(예외 결정표)를 사용자에게 건넨다
5. 바퀴마다 `lab/rounds/roundN.md`에 한 일·숫자·드러난 문제·보완을 남긴다

## 발굴 중 점검 주기
- 새 후보 **100개마다** 멈추고 보완 점검: `LAB stats --stages`(출처별 오판율)·`LAB drops`(사유 유형)로 무엇이 틀렸는지 보고, 스킬을 고친 뒤 영향받은 아이디어를 다시 확인하고 다음 웨이브를 시작한다
- **보완 점검 때 안전장치도 점검한다(사용자 지시 2026-09-27)**: 100개 묶음이 끝날 때마다 조기 발견 장치 자체를 실측으로 다시 맞춘다 — ① `lint` 개념 중복률·필수 칸 누락률(기준 10%·20%가 너무 느슨/빡빡했나, 놓친 중복이 조사 단계에서 나왔나) ② 20개·50개 파일럿 점검의 오류율(3개 표본으로 충분했나, 틀린 항목이 무엇이었나) ③ 선별 보정 결과(선별 탈락 3개 중 살아난 수 → 선별 기준 조정) ④ 할당표 대비 실제 분포와 기법·분야별 생존율(할당 숫자 재조정) ⑤ 웨이브 크기(25~30줄)와 묶음 크기(100)가 속도에 맞았나. 바꾼 기준·숫자는 `lab/rounds/IMPROVEMENTS.md`에 회차별로 적는다
- **복리 학습 루프(사용자 지시 2026-09-27, 보완 #16: "발굴할수록 배수로 능력 향상")**: 웨이브를 보내기 전 메인이 `py -3 scripts/knowledge.py`로 `lab/knowledge/`(titles.tsv 옛 카드+탈락 사유, patterns.md 이긴 구조 카드, yield.md 기법·출처별 적중률)를 새로 만든다. 발굴·조사 조사원은 `templates/CORE_RULES.md`를 먼저 읽고 titles.tsv는 grep만, patterns·lessons는 한 번 읽고, 끝날 때 배운 것 1~3줄을 lessons.md에 남긴다. 효과가 곱해지는 이유: 생존이 늘면 씨앗(patterns)이 늘고, 탈락이 늘면 즉시 피할 길(titles·lessons)이 늘며, 적중률이 쌓이면 웨이브 배분이 정확해진다. 메인은 웨이브마다 과정 개선 1개를 찾아 바로 적용하고 IMPROVEMENTS.md에 적는다
- **군살 빼기(사용자 지시 2026-09-27, 보완 #17)**: 조사원이 매번 읽는 분량이 속도를 늦춘다. 공통 규칙은 `templates/CORE_RULES.md` 한 장에만 두고 각 지시문은 첫 줄에서 그것을 가리킨다(보완마다 지시문 4개 끝에 같은 규칙을 덧붙이지 않는다). 큰 파일(titles.tsv 500KB·research.md·harvest.md)은 grep·절 단위로만 읽게 한다. 중복 파일(all_titles.txt)은 없앴다. 새 규칙을 넣을 때는 CORE_RULES에 넣을지 해당 지시문에만 넣을지 먼저 정한다
- **하베스터가 스스로 버린 후보도 표본으로 본다**(점검 #2: 하베스터 사전 필터가 구간 후보의 91%를 버렸고, 유명세 발굴에서는 '무료 제품 존재'를 규모 확인 없이 적용했다). 웨이브마다 하베스터 drop 3개를 골라 이유가 **지금 기준**(규모 링크, beatable, 행동 증거, 유입 길)과 맞는지 메인이 확인하고, 어긋나면 그 웨이브의 같은 유형 drop을 전부 다시 본다
- 점검 때마다 `LAB timing`으로 재검토 날짜가 온 **타이밍 대기** 아이디어를 다시 조사한다(날짜가 오기 전엔 건드리지 않는다)
- 살아 있는 수는 **4단계(검증 완료·가짜 문 테스트 대기) 이상에 있는 독립 제품만** 센다 — 관문 6개 모두 통과 + 메인 표본 검증 + 레드팀을 마친 것. 3단계(조사·관문 심사 중)는 관문 하나라도 미통과면 세지 않는다(2026-09-25 사용자 지적: 수익 계산 미통과 i1237·i1318을 살아있다고 세던 오류 정정). 묶음 부가 기능은 핵심 아이디어에 포함, 따로 세지 않는다
- **보완할 때는 과정의 실수만이 아니라 판정 기준 자체의 사각지대도 본다**(사용자 지시, 6회차: 수익성을 유료 고객 수로만 재다가 '무료로 유명해져 돈 되는 길'을 통째로 놓쳤다). 점검 때마다 기준마다 이 질문을 한다:
  1. 이 기준은 **어떤 방식으로 성공하는 제품을 처음부터 떨어뜨리나?** 이 기준으로 채점하면 떨어졌을 유명 성공 사례(무료 커뮤니티, 욕망형 앱, 경쟁사가 있던 시장의 후발 주자, 해외 틈새 도구)를 하나씩 대 본다
  2. Drop 사유 분포(`LAB drops`)에서 한 유형이 몰려 있으면(예: competitor 316) 그 유형의 기준이 너무 넓은지 표본 5개를 다시 읽는다
  3. 증거 규칙이 **특정 사람들만** 세고 있지 않나(글 쓰는 사람만, 한국어만, 공개 웹만)
  4. 숫자 목표가 **한 가지 모델**만 가정하지 않나(구독만, 한국만, 유료만)
  5. 지금 증거가 얇은 이유가 '없어서'인지 '막 생겨서'인지(타이밍)
  찾은 사각지대는 사용자에게 목록으로 먼저 보여 주고, 동의한 것만 기준표·관문·템플릿·`lab.py`·대시보드에 한꺼번에 반영한 뒤 버린 아이디어 중 영향받은 것을 재검토한다(예: `templates/FAME_REVIEW_PROMPT.md`, `templates/CRITERIA_REVIEW_PROMPT.md`)
- **고친 뒤에는 `py -3 scripts/selftest.py`(보드 복사본으로 import·apply·audit·gate·move·rank·list·market·drops 전 과정 점검)를 돌려 실패 0을 확인하고, 대시보드를 재시작해 카드 표시까지 본 다음에** 발굴을 다시 시작한다(사용자 지시: "보완들이 완벽하게 작동되면 그때 아이디어 조사를 다시 시작"). 새 기능을 넣으면 selftest에도 검사 항목을 더한다
